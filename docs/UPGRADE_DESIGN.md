# CyberScientist 竞赛与科研升级总体设计

- 版本：v1（2026-09-27）
- 基线：`Raven1119/CyberScientist@a48a780`
- **本文件的作用**：固化用户与设计者多轮讨论形成的共识，是后续所有任务卡的依据。
  - 任务卡与本文件冲突时，**以本文件为准**，并在 `docs/DECISIONS.md` 记录冲突情况。
  - 本文件的修改只能由用户发起。

---

## 1. 用户意图

1. **当前第一目标**：在第四季“科学骑士大师赛”中超越榜单头部选手。很多头部选手已经在大部分题目上拿满分。
2. **长期目标**：做成“科学家”，而不是“做题家”。系统在比赛里学到的能力，要能迁移到**没有评测器**的真实科研中。真实科研场景的专门优化推迟到比赛题目做好之后。
3. **稳定性要求**：新能力不能让 Run 卡住。能交给代理自主处理的，就交给代理；代码负责兜底。
4. **尽量复用现有机制**：能用经验系统和 skills 解决的，就不改控制器。
5. **自主推进**：Codex 施工时自主完成，不向用户提问。

## 2. 赛制与评分事实（已核实或由用户确认）

| 事实 | 来源 |
|---|---|
| 单题展示分 = 科学分 × 轨迹因子。轨迹因子 = clamp((trace_score − 30) / 40, 0, 1)，即 70 分以上为 1，30 分以下为 0 | 用户确认；MCM 两条提交的数据吻合 |
| **`displayScore` 是权威分数**。平台可能在赛后复评：Hubbard attempt 36189 的 `harbor_score=100`、`trace_score=70.525`，但 `displayScore=80`，`updatedAt` 比所在轮次晚 3 天，分项字段没有同步更新 | 平台原始 JSON |
| 每个邮箱对每道题有 10 次提交机会；实验（派生）邮箱的提交不占主邮箱（收割邮箱）的次数 | 用户确认 |
| 提交速度不计分 | 用户确认 |
| 每轮约 24 小时，每轮 9–10 道题；比赛期间其他选手的分数分布公开可查，提交内容在赛季结束后公开 | 平台 API |
| 平台会重放提交（`harbor_replay_executed=1`），提交包必须能在干净环境中复现 | 平台 JSON |
| 轨迹准入规则、平台选择哪些轨迹行参与评判的规则，以 `contracts/arm_protocol.json` 快照为准；文档中的 `trace_quality` 只按步骤数分档，展示出的 `trace_score` 另有未公开的评审层（协议中称为 conviction 层） | 协议快照 |
| 云端评分器经常抽风：长时间排队、先出一个分再被改正 | 用户经验，以及 `docs/DECISIONS.md` |

## 3. 竞争格局判断

- **饱和题**（例如 MCM）：大量提交满分。能拉开差距的只剩轨迹是否 ≥70，以及覆盖了多少题。
- **平台题**（例如 XAS，约 510 个提交几乎都卡在 67.9）：谁先找出大家都在丢分的那个分量，谁就胜出。
- **前沿题**（例如 Hubbard NQS）：靠真正的科研能力拉开差距。
- **头部选手的做法**：直接用通用编程代理（Codex、Claude Code），并把实验性提交当作反馈来源。我们的优势应当来自三点：**本地评分、证据纪律、并行吞吐**。

## 4. 设计原则

| 编号 | 原则 |
|---|---|
| P1 防卡死 | Run 内的新能力一律是可选增强，产出物带状态（none / partial / ready），缺失时回退到原路径。只有不可逆节点（花钱、提交）可以设门禁，而且判定要快、结果确定，并有覆盖入口。代码负责检测和升级处理，代理负责修复（见 §6.8）。 |
| P2 代码与知识的边界 | 凡是涉及凭据、花钱、不可逆操作、跨 Run 状态、能力开关的，写进**代码**；凡是涉及判断、方法、策略的，写进 **skills / 经验 / 系统提示词**。硬约束不能只写在 skill 里。 |
| P3 平台反馈的定位 | 平台反馈只用于诊断和校准，主要优化回路放在本地。实验邮箱可以反复提交，但**每次实验提交前必须写下一句预测**（改了什么、预计哪个分量怎么变），出分后记录预测是否成立。 |
| P4 轨迹诚实 | **表达层可以改**：标题、组织方式、叙述、选哪几行日志做锚点、给真实文件加 artifact 步骤、解释“出错 → 修复”。**事实层不可改**：工具调用或结果是否存在、输出原文、时间戳、退出码、费用、数值。每一步都要能对应到真实记录，并由代码做引用校验。事后补写的注释如实标注，使用写作时的时间戳。目标是“每一句都可核对，并且写得好”，**不是**“让评审识别不出改写”。 |
| P5 逆向评测器的边界 | 可以逆向**评分逻辑**：公式、门槛顺序、容差、哪些字段参与计分、回执格式。**不能**通过构造提交去套出隐藏的参考答案或测试数据。 |
| P6 预算 | 代码只执行用户明确设置的授权上限，不预设额度；上限之内由大脑判断题目难度和成本并分配。 |
| P7 Bohrium-first | 科学计算在 Bohrium 上执行，交互式沙箱也包括在内。沙箱结果经网关记录后，与 Job 结果同等作为正式证据。 |
| P8 证据如实 | 延续 AGENTS.md：不知道就记为 unknown，不编造，Demo 不冒充真实结果。 |

## 5. 决策清单

| 编号 | 决策 |
|---|---|
| D-01 | 采用 P1–P8 |
| D-02 | 并行 = 简单的多 Run 并行：用户逐题手动导入并启动，做好持久化。物理并行度预期 3–5 个 Run；运行环境是用户的笔记本（14900HX + 4080，WSL2） |
| D-03 | 分诊由大脑在题目开始后完成，通过系统提示词、经验和 skills 实现，只是建议，不设代码层的状态机。不做轮次级的分诊会话，也不自动重新分诊，只能由用户手动修改 |
| D-04 | 跨题视角通过全局经验和系统提示词实现；Run 之间不通信 |
| D-05 | 环境事实（镜像内容、API 地址、机器规格等）作为**全局经验中单独的一类**：只由代码根据真实回执自动生成，免审批，带观察时间和出处，过期或被新回执推翻时自动标记为待复核。研究思路类的全局经验仍需用户审批 |
| D-06 | 模型在导入题目时按角色选择。默认大脑用 Astra，执行器用 gpt-6 sol，均走 Codex。模型名由配置管理，可用性由连接探针确认 |
| D-07 | 不做并行探索（一题多跑、路线协作）。以后如果做，先用评测集测出方差再决定 |
| D-08 | 分数拆解分两层：**代码自动采集**每次提交的分项、违规规则和评测器消息，存进账本并放进审阅输入；**对这些数据的解读**沉淀为题内或全局经验 |
| D-09 | 经验按角色分发：同一个经验库，增加 `audience`（brain / executor / both）字段，注入时按角色过滤。经验生成（整理）流程也要随之改进 |
| D-10 | 评分分为“暂定 / 确认”两级；本轮结束后继续轮询一段时间，以捕获复评；以 `displayScore` 为准，分项不一致时标记出来；异常分数不进入经验 |
| D-11 | 收割时允许选择任意一个已出分的实验提交，但非最高分、暂定分、分项不一致时要给出警示 |
| D-12 | 交互式沙箱：网关开放 `bohr sandbox`（2.7.8）的 create / exec / files / delete / list / describe；账本记录每个沙箱；创建时强制带超时，禁止 `--never-timeout` 和 `--inherit-auth`；Run 结束时回收，重启时对账清理孤儿；上限由用户设置 |
| D-13 | 提交前必须用题目指定镜像**在干净环境中复跑**一次入口脚本，提交包里的运行日志就来自这次复跑（由 skill 规定） |
| D-14 | 代理可以直接编辑轨迹叙述而不重跑 Job（遵守 P4），由封存流程做引用校验 |
| D-15 | 本地评分器 = **skill**（教代理如何根据评分标准搭建评分脚本并在题目镜像中运行）+ **薄代码契约**（统一接口：输入产物、输出 JSON，包含总分、分项、置信度、备注；控制器把本地分和平台分配对存进校准表） |
| D-16 | 逆向顺序：先选一道**已经跑过、轨迹有得分的简单题**逆向轨迹评分器；再结合本地科学评分器，做出第一个成功的本地评分器 |
| D-17 | 评测集放在本地评分器完成之后再建：从第四季已结束的题目中选取，**按实际得分分布和评测难度选题，不看平台的难度标签**；分快速层和困难层；每道题至少跑 2 次 |
| D-18 | 平台排行查询：给大脑一个只读工具，用于查看本轮其他选手的得分分布，服务于分诊 |
| D-19 | 模型出现 429 或额度耗尽时要如实标记，并被防卡死机制接住 |
| D-20 | Kimi 执行器 `pending` 状态导致工具调用配不成对的问题暂不处理 |

## 6. 目标架构（按组件）

### 6.1 Run 与并行
- 取消“同时只能有一个活跃 Run”的限制，工作区锁改为按 Run 加锁。
- 全局资源只做**可见性**，不预设上限，用户可以自行设置：Bohrium 的 Job / 沙箱并发与配额、模型调用。
- 前端提供“本轮总览”：每道题的状态、得分、花费、是否卡住。
- 每个 Run 的模型配置在导入时冻结进快照。

### 6.2 计算层
- 沿用 Job 网关和账本。
- 新增沙箱网关和沙箱账本（D-12）。
- exec 的输出经脱敏后记成事件，作为轨迹中真实的工具调用与结果。

### 6.3 提交、评分与邮箱
- 额度按 **(邮箱, 题目)** 计数。
- 评分分两级，赛后继续轮询，检查分项一致性（D-10）。
- 收割可选任意已出分的提交（D-11）。
- 每次实验提交必须附带预测（P3），出分后自动核对。

### 6.4 轨迹
- 封存流程和本地准入**严格复刻**平台的选行规则（`trace_row_selection`）。
- 事件投影提供事实层，代理叙述提供表达层，两者合并前做引用校验（P4、D-14）。
- 本地轨迹预测器用实验提交得到的真实 `trace_score` 来训练校准，目标是稳定判断“能否过 70”（有余量更好）。

### 6.5 本地评分器
- 采用 skill + 契约 + 校准表（D-15）。
- 评分器和校准记录属于题目，跨 Run 复用。

### 6.6 经验与 skills
- 增加 `audience` 字段（D-09）。
- 环境事实作为单独一类（D-05）。
- 分诊策略、分数拆解思路、轨迹写作、沙箱使用、干净环境复跑，都以 skill 或经验的形式交付。

### 6.7 模型选择
- 大脑和执行器分别配置模型和推理强度（D-06）。
- 提交时带上的 `modelTag` 要与实际运行时一致。

### 6.8 防卡死（分层）
1. **检测（代码）**：Run 处于 running，但没有活跃 Trial、没有进行中的 Job 或沙箱操作、没有待处理的审阅，且持续 **5 分钟**，即判定为卡住。
2. **唤醒（代码）**：唤醒大脑，并附上诊断信息：当前每个组件在等什么。
3. **修复（代理）**：大脑在自己的动作集合内修复。
4. **兜底（代码）**：
   - 大脑会话死亡时，重启会话；
   - 需要用户授权的，等待用户；
   - 连续两次修复失败，暂停 Run 并通知用户；
   - 模型限流或额度耗尽，同样走这条路径。

## 7. 分阶段路线

| 阶段 | 目标 | 退出标准 |
|---|---|---|
| **阶段 1：缺陷修复**（CS-UP-01） | 修掉会直接影响正式提交的缺陷：选行规则、邮箱额度、评分两级、收割 | 任务卡中的验收全部通过，并已 push |
| **阶段 2：能力建设** | 多 Run 并行与持久化、沙箱网关、模型选择、防卡死分层、429 处理、环境事实类经验、经验 `audience` 字段、实验提交预测字段、排行只读工具 | 3 个 fake Run 并行跑通；沙箱全生命周期测试通过；任一卡住场景都能自动恢复或升级处理 |
| **阶段 3：逆向与本地评分器** | 轨迹编辑与引用校验；在一道已跑过、有轨迹得分的简单题上逆向轨迹评分器；本地科学评分器 skill + 契约 + 校准表；做出第一个与平台分数吻合的本地评分器 | 在该题上，本地预测的展示分与平台分的偏差在题目容差以内，并有校准记录 |
| **阶段 4：评测集** | 按 D-17 建立 | 两层评测集可以一键运行，输出分数、耗时和花费 |
| 以后 | 按模型能力标注题目；一题多跑；真实科研场景的专门优化 | 另行讨论 |

## 8. 明确不做或推迟

- 路线之间协作的并行探索、Run 之间通信；
- 轮次级分诊会话、自动重新分诊；
- 代码层面的预算硬限制（用户显式设置的授权上限除外）；
- Kimi 工具调用配对问题；
- 伪造或优化“无法被识别为改写”的轨迹；套取隐藏参考答案。

## 9. 风险与未知

- 笔记本睡眠、系统更新、WSL2 挂起，都会让所有 Run 同时中断。比赛期间应关闭睡眠、推迟更新。
- 多个 Run 共用一个 Codex 账号，可能触发限速或耗尽额度。
- `trace_score` 很可能有大模型评审参与，存在噪声；逆向时要先测同一个包重复提交的一致性。
- 平台复评可能在“最终”分数出来之后仍然改分。
- 旧版 Job 客户端现在依赖 `openapi.dp.tech`，`job submit` 和 `job list` 在该地址下尚未经过真实验证。另外，配置中的 `host_overrides` 可能覆盖掉这次修复。
