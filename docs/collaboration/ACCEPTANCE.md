# 验收与交付证据

## 1. 必须通过的三组行为测试

测试接入真实控制器与临时 SQLite；原生进程用可控假协议服务替代。不能只测试一个独立样例类。两种运行时共用行为断言，各自保留协议适配测试。

| 组 | ID | 场景 | 断言 |
|---|---|---|---|
| 并行与静默 | T1 | 大脑在 barrier 等待结果，执行器持续产生事件，用户读取 SSE/发送控制 | 执行器事件继续提交，UI 能读到；控制门禁不等待大脑；同会话只有一个 pump |
| 并行与静默 | T2 | 有效观察 → 大脑返回 SILENT | 执行器 prompt/steer/cancel 调用增量均为 0；任务、会话、目录、经验快照不变；只更新大脑状态 |
| 并行与静默 | T3 | 事件突发、纯心跳、大脑自己的输出、重复观察范围、监督故障/额度耗尽 | 审阅单飞且合并；无新有效变化不调用模型；无自激循环；shadow 失败不暂停执行器 |
| 请求与投递 | T4 | MCP 执行器提交 none / async / blocking 检查点；同 key 重试和冲突 | 工具不等待大脑；请求原子持久化；重复不增审阅；不同内容冲突；blocking 先 YIELDING 后确认等待 |
| 请求与投递 | T5 | 执行器忙时生成指导，再到自然检查点或空闲回合 | 指导持久排队，无忙时拒绝后丢失，无普通 cancel；只选一个投递渠道；ACK 与应用证据分开 |
| 请求与投递 | T6 | 大脑要求重新组织证据；执行器提出异议、补报；阻塞请求收到 SILENT/错误 | observe 沿同一 Trial/会话继续，无双方互等；异议留证；无有效阻塞答复不自动放行 |
| 请求与投递 | T7 | 原生 turn 结束但没有实验完成报告；未知终态；已有 Trial 明确交付 | 不误判科学完成；终态先更新 busy 再通知；明确交付进入审阅而不冒充评分通过 |
| 请求与投递 | T8 | 审阅期间暂停/换目标/换 Trial；发送与暂停交错；STOP | 旧指导不按新目标投递；已发出但未知的结果不谎报撤销；STOP 先关门，收到终态才已停，Job 独立 |
| 恢复与产品 | T9 | 在检查点提交、结果入队、指导发送三个边界重启 | 请求不丢、不重复新建科研任务；在途不明先对账；数据库迁移重复执行安全 |
| 恢复与产品 | T10 | 观察投影包含执行器 raw reasoning、密钥样本、跨 Run 引用；资料不足 | 大脑自动输入无原始推理/密钥/越界内容；未知不编造；截断和未读可见；能力令牌不能操作其他 Run |
| 恢复与产品 | T11 | 编辑经验、回滚，再创建下一 Trial | 当前 Trial 正文/版本不变；下轮采用新修订；大脑/执行器确实读取正文；失败与旧版本保留 |
| 恢复与产品 | T12 | 浏览器打开工作台、开关监督、请求审阅、查看指导；重连页面 | UI 来自后端真实状态；关闭监督不停止执行器，未发 shadow 指导失效；重连不重启 Run |

T1 使用 `asyncio.Event` 等确定性 barrier 控制交错，不靠长 sleep 猜测并发。T2 对控制器发向执行器的实际调用记录做断言，不能只断言一个 `silent=true` 字段。

补充协议测试覆盖本机核实的初始化、事件命名、active turn ID、反向 RPC、stderr 持续消费和未知终态；不能用错误的旧 fixture 证明新协议正确。

## 2. 一条完整演示与一条有界真实探针

### 确定性演示（无付费调用）

使用独立临时目录和明确标记的合成证据，走真实 HTTP/MCP → 控制器 → SQLite → SSE 路径：

```text
启动授权的测试 Run
→ 执行器进行步骤 A，产生可观察事件
→ 大脑审阅并 SILENT，执行器继续 B（验证没有额外输入）
→ 新检查点产生有效变化，大脑生成 STEER，执行器仍忙
→ 指导留 queued；执行器到自然边界收取并 ACK
→ 执行器按指导补充证据，仍沿同一 Trial
→ 下一次审阅期间用户暂停，迟到指导失效
→ 重启服务，仍可见审阅/ACK/证据，无重复外部操作
```

保存简短事件时间线、执行器输入调用记录、状态断言和 UI 截图。合成指标必须标 `synthetic`，不能与比赛成绩混用。验收 fixture 可脚本化大脑选择，不代表模型实际判断能力。

### 真实 CLI 探针

已有明确费用授权时，用可用的 Kimi/Codex 配置执行一个小型、非科学、无比赛提交的临时文件任务，验证两个独立原生会话、真实事件采集、一次静默审阅和一次边界指导/ACK。两种运行时分别记录：版本、有效模型配置、握手、会话建立、模型往返、MCP 工具、边界投递、取消/恢复的实测状态。

有些项无凭据或无额度时明确标 `not_run / blocked`；把可以运行的探针命令与具体缺项交付，不能写“全部通过”。初始化握手只能证明协议连接，不能证明工具、模型、恢复或科学效果。

## 3. 一次任务的最终交付

复用仓库自己的测试/构建命令（当前状态文档使用 `uv run pytest tests/ -q` 与 `cd apps/web && npm run build`；本机先核对）。新增测试纳入原套件，现有全局功能不得因 shadow.enabled=false 退化。

`docs/collaboration/IMPLEMENTATION_RESULT.md` 只需要三部分：

**代码审计与改动**：本机 HEAD/dirty 状态、参考发现的复核、修改路径、必须的设计调整。

**执行过的验证**：准确命令、退出码、测试计数、完整演示证据、运行时能力矩阵、实际启动方式。未执行不写通过。

**尚未验证与阻塞**：真实模型/平台/浏览器中哪些未完成，原因与已交付的可执行入口。分开工程通过和科学得分未测。

更新 `STATUS.md` 和当前有效指令；交付工作树，不擅自 commit/push。此文档中的 T1–T12 是同一任务的验收场景，不拆成后续阶段或等待第二次批准。
