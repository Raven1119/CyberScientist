# 轨迹评分机制：公开源码与本人历史提交的交叉逆向

本轮找到 Playground CLI 作者公开的 `trace-score-cli`，把先前的分数分布分析推进到源码和离线行为验证。**公开 v6 的合成公式、上限、裁判输入和解析缺陷已可复现；历史 v8 的完整内容评分还未复刻。** 尤其不能把一次转换丢失造成的低分解释为研究能力不足。

本轮未调用研究模型或评分模型，未新建 Run、Job、沙箱、Attempt，未读取其他参赛者的提交。仅获取公开代码与元数据、读取本人已有封存文件、执行文件转换及应用测试。原始资料、源码克隆和审计输出留在忽略目录 `.package-checks/trace-score-source-20260928/`；本报告不列账号或 Attempt ID。

## 已解出的公开 v6 评分结构

源码 [`buildChecklistReport`、`automaticScoreComponents`、`automaticScorePolicy`](https://github.com/Osgood001/trace-score-cli/blob/81c434907e7b0a2feccc79236f6601f7abbc1d84/src/index.ts#L2980) 给出：

```text
C_raw = clamp(100 + 所有已触发负项的 score_effect, 0, 100)
C     = min(C_raw, 检查表上限)
P     = 两名裁判的 provenance_sufficiency 平均值
H     = 两名裁判的 hack_risk 平均值
T_pre = 0.55 C + 0.25 P + 0.20 (100 - H)
T     = min(T_pre, 检查表上限, 语义/证据/分歧上限)
```

这里的 `C` 是检查表分，**不是**输出中另一个 `rule_score/trace_quality_score`。源码把后者提供给裁判作上下文，但并未直接代入上述加权公式。正项 Q01–Q06 的 `score_effect` 为 0，主要参与标签和高质量分类；不能把每条正项理解为奖励分。

两名裁判分别采用常规审查与更强调质疑的系统提示，使用同一配置的模型；这不证明它们统计独立。H、P 分别取均值并保留一位小数；分歧为两名裁判在 H、P 两个维度上的最大绝对差。完整回执里缺少这两个裁判的原始数值，不能从一个 T 唯一反推出 H、P。

| 公开 v6 触发条件 | 上限 | 对最终判定的作用 |
|---|---:|---|
| 轨迹/产物/上下文回执冲突、跨题复用、缺少可解析模型活动等硬完整性失败 | 20 | `block`；还包括若干严重泄漏/来源问题 |
| N06 不受观察支持的执行或伪造 | 39 | 检查表限制；本身不必触发 `block` |
| N09 缺少被识别的计算证据，或 N13 证据过少 | 49 | 无法靠其他项补到接受区 |
| N12 重复膨胀，或 N15 时间/用量异常 | 69 | 无法到 70 |
| 平均 H ≥ 80，或输入的裁判判定为 `likely_hack_or_unclean` | 29 | `block` |
| 平均 P < 30 | 59 | 低来源证据可导致 review，即使没有作弊判断 |
| 两名裁判分歧 ≥ 30 | 69 | `review` |

**上限不是固定得分。** 例如本轮合成测试中，低基础分加高风险的输入只得 0.2，仍属于 29 分上限的 block。最终先看硬失败/语义失败，再看 T < 70 或分歧；若缺关键完整性回执，另可为 `insufficient_evidence`，其余才是 accept。公开代码中精确接受边界是 70；这个边界的历史 v8 一致性仍需区分于源码事实。

还有一个易误解的细节：双裁判内部的 `needs_review` 标签本身不必阻止最终 accept。合成输入 C=100、P=65、H=40、分歧=0，在公开代码中得到 83.25 / accept；最终 policy 检查的是更具体的风险、分歧及分数条件。不要把不同层级都叫作一个“通过”。

该结构解释了此前两类疑问：

- N08 的 `score_effect=-18` 是对 C 的扣分；无上限干预时只使 T 少 9.9。不能把回执中的负项直接从最终轨迹分扣除。
- 缺少低分原因列表也可能只有 29、59 或 69：检查表原因与语义/证据上限是不同通道。63 份 v8 回执中，12 份非 accept 没列检查表负项；26 份恰落在 29/49/59/69。这与源码结构相容，但单看 69 不能判定是哪一项上限生效。

63/63 历史分数落在 0.025 的格点上，也与整数双裁判平均再用 0.55/0.25/0.20 合成相容。**相容性不等于确认 v8 权重**：其他算法也可能产生同样格点，且隐藏裁判数值没有取回。

## 裁判实际读到了什么

公开 v6 [`scoreTraceExcerpt` 与 `automaticScorePrompt`](https://github.com/Osgood001/trace-score-cli/blob/81c434907e7b0a2feccc79236f6601f7abbc1d84/src/index.ts#L3076) 没有向模型传完整原生轨迹：

- 取最前 15、最后 20 个事件，以及最多 25 个均匀抽样索引；保留所有 user 和标记为 final_answer 的事件。索引去重后数量可少于 60；不是严格“全文前后加 25 条中间事件”。
- 每个事件先折叠空白，再只保留开头 900 个字符。函数体尾部、后半段日志、成功返回行可能不在裁判输入中。
- 题目只给前 5000 字符；文件递归列举排序，提供前 40 个文件的摘要。文本文件不超过 200000 字节才读文本摘要，摘要最多 6000 字符；图片二进制通常只有文件名、大小和哈希，**这里不是把图像直接交给视觉模型**。
- 确定性检查则遍历自己的解析事件，并把检查表、统计量、工具模式、风险提示等摘要也送进裁判。语义模型看不到全文，不等于确定性部分也只看相同片段。

本轮 100 个合成事件只产生 53 个摘录事件；每条尾部标记均被截掉。FigQA E010 的 83 个转换事件只有 50 个进入直接事件摘录，E011 的 51 个只有 40 个。E010 把代码分成三段打印过，仍不能据此证明裁判收到了完整代码；文件作为产物进入摘要与仅在工具输出里打印，是两条不同的证据入口。

这给出一个更贴近实际的模型：**分数由平台真正读到的证据决定；研究执行正确、原生轨迹保存完整、提交转换无损、裁判可见内容充分，是四个分别需要成立的事实。**

## 已离线复现的故障与同题对照

三份 FigQA-0177 输入均先按平台历史接收回执的原生轨迹 SHA-256 选择本机相同字节文件，再用固定的本机 CLI 转换。下表的本地检查表不是新平台评分；未提供历史 worker 上下文或重新调用裁判。

| 阶段 | 历史科学分 / 轨迹分 / 展示分 | 本轮固定 CLI 的转换 | 公开 v6 对转换文件的检查 |
|---|---|---|---|
| E008 | 100 / 5.8 / 0 | 43 个原生事件 → **1 个 error** | N04、N09、N11、N13；检查表 0，上限 20 |
| E010 | 100 / 49 / 49 | 94 个原生事件 → 83 个 ARM 事件；36 对命令 | 仅 N09；检查表和上限均为 49 |
| E011 | 100 / 96.375 / 100 | 72 个原生事件 → 51 个 ARM 事件；22 对命令 | 无负项；检查表 100，上限 100 |

### E008：一条普通传输错误使整份轨迹被误判格式

本机 CLI `parseTraceSteps` 在 Codex 检测前调用 `opencodeEventLike`。后者只要看到任意 `type="error"` 就判作 OpenCode；Codex 原生流也会有这种顶层错误。于是转换器只保留那条重连超时，丢掉 `item.*` 中的推理、执行和文件变更。

本轮另用完全合成的最小对照验证：相同 Codex 工具调用和回复，正常输入转换为 `thought/tool_call/tool_result/thought`；仅加一条顶层传输 error，便只剩 `error`。这是**当前固定 CLI 的已复现缺陷**。历史 E008 回执同样说没有工具/模型活动，并触发 N04/N09/N13，与本次转换完全相容；但没有拿到当时服务端最终归一化文件，仍不把历史唯一根因写成已由服务端证明。

另外，公开 v6 scorer 自身没有识别这种 Codex `item.*` 原生结构：三份 native 文件都被读成 role=unknown、0 个 assistant、0 个工具。说明不能绕过转换直接以“原生文件完整”为由认定评分器能理解它。

### E010：真实执行未命中“计算证据”的启发式

公开 `firstPositiveComputationEvent` 用同一事件文本的关键词组合识别计算，不重建命令到返回值的真实执行关系。它要先命中计算类词，再命中产物路径或特定完成词；底层 exit_code 不直接参与该函数。合成测试中 `python src/calc.py` 的调用加成功返回数值 `42`，仍未识别为计算证据。

E010 实际有像素扫描、基线判别、源码打印、运行输出和答案回读；但转换后确实没有事件满足该启发式，触发 N09，重现历史 49 分上限。E011 首次命中该检测的竟是**用 Python 清点 README、源码、日志和 outputs/answer.txt 的字节数及哈希的命令**，不是主要的像素计算。它同时含计算关键词与产物引用，足以让公开 v6 的 N09 消失。

这没有证明 v8 只看同样的词，更不意味着应插入某个词获取分数。它证明了一种实质性失配：**真实科学计算的有无，与检测器识别到的“计算证据”可以分离。** E011 还加入了源码、复现包和独立重放，不能把历史 49→96.375 全部归因于这一处检测。

### 导出还会改变来源证据

本机 CLI 的 Codex 转换只覆盖部分事件，`file_change` 不进入 ARM 行，命令的 `exit_code` 也不保留为结果字段。原生副本仍可在包内，但这不保证它会被实际评分路径使用。官方 CLI 的自动包入口另生成占位 `src/reproduce.py`；兄弟目录中的科学源码不会仅因为被执行过就自动纳入 `--outputs`。应核对包中实际科学源文件，不能仅数“有 reproduce.py”。

## v8 能确认到哪里

v8 回执新增 N18，描述“过程证据不足以跨过满额门槛”，其 `score_effect=0`。4 条触发样本的轨迹分分别为 2.25、5.8、29、69。由此能确认：**0 扣分不等于无准入影响**；回执建议保留重复的成功科学执行或可见的题目专属源码创建。不能由这 4 条推出次数阈值、准确布尔条件或全题通用的强制重跑规则。

本人还有不支持简单口号的反例：FigQA-0178 最终轨迹 86，回执仍指出缺视觉回执和完整源码；一些数学题以推导和小型验证得到高轨迹分；Lean E002 轨迹 82.75 而科学分 0，后来轨迹 75.925 的 E009 科学与展示分反而 100。**科学正确性、执行证据质量、来源可信性不能合成一个“工作做得好”的单指标。**

历史总分合成则已在 63 份直接回执上核对：

```text
display_score = harbor_score × trace_factor
accept → factor = 1
review → factor = trace_score / 100
block  → factor = 0
```

这是该批历史 worker 的实测回执关系；不是公开 scorer 自己的 Harbor 合成公式。主办方通过用户告知的 30–70 线性公式仍有冲突，未用源码发现覆盖或改写这条外部说明。官网当前通用 ARM 的“Dockerfile 存在就有 executability 结构分”也属于另一评分路径，详见[官网契约与满分前对照](OFFICIAL_SCORING_AND_FULL_SCORE_TRANSITIONS_2026-09-28.md)。

## 对 CyberScientist 的实质启示

1. **优先让证据从运行时到提交包保持可追溯。** 用格式签名识别 harness；一条通用 error 不应覆盖整个流。以工具调用、返回、文件修改、真实退出码的保留情况做转换测试，并保留原生行号到提交行号的映射。不要通过删除失败记录修复误分类。
2. **把科学源代码、真实输入引用、执行回执和最终输出作为同一条来源链封存。** 摘要只做索引，原始证据保留；真实执行器返回什么就记录什么。自动生成的壳脚本不充当科学复现入口。
3. **评价预测器先解释确定性风险和缺失输入。** 公共 v6 的 reducer 可精确复现，历史 v8 内容到 H/P 的映射仍未知。更有依据的产物是“为何可能被挡在 70 以下、评分器可能看不到什么”的诊断，而不是用事件数拟合一个伪精确分数。
4. **保持大脑稀疏监督。** 上述完整性保证属于运行时记录和提交适配器，不需要大脑每一步主动核查、强制重跑、先读轨迹后作答或不断生成审计文字。下一轮真正要测的是证据传递修复后评分稳定性，而非只比较更长的提示词。

这些建议由本轮缺陷与反例支持；还没有通过新的真实提交验证评分增益。本轮没有更改全局 CLI、运行时内核或生产预测器，也没有自动批准全局经验。

## 可重复验证与交付

新增 `checks/audit_public_trace_scorer.mjs`：执行前核对公开源码 SHA，移除 CLI main 后调用原函数；拒绝其他版本，禁用本进程 fetch，不调用裁判，使用明确的合成输入检验公式、上限、边界、解析和截断。可选固定 CLI 仅执行本地 `trace convert`；实际历史分析报告含原始证据，应输出到忽略目录。

```bash
PATH=/home/wmywb/.local/bin:$PATH node --experimental-strip-types \
  checks/audit_public_trace_scorer.mjs \
  --source .package-checks/trace-score-source-20260928/upstream/src/index.ts \
  --playground-cli /home/wmywb/.local/lib/node_modules/@paper2arm/playground-cli/dist/index.js \
  --out .package-checks/trace-score-source-20260928/offline-audit.json
```

本轮此工具的 18 项离线断言通过；三份历史轨迹分别以 native 与本机 CLI 转换形式检查，共 6 次，无新平台评分。Node 为 Linux 22.17.0。最初直接对安装在 node_modules 中的 CLI `.ts` 使用 type stripping 被 Node 拒绝，未产生转换；之后使用已安装、已核对哈希的 `dist/index.js` 完成，未更新客户端。完整应用验证结果记入 STATUS。

有界审查已核对：源码版本锁在导入之前验证，合成输入不执行科学命令，历史分析不提供伪造 worker 回执，子进程仅走文件转换入口，临时模块在退出时清理；真实输入正文不进入可提交报告。提交文件为脚本及 Markdown，未暂存忽略目录、下载包、数据库或原始回执；对这些文件的凭据模式与邮箱扫描未发现命中。

可用边界：我们已经解释并复现了评分链中的多个不连续点和一个会丢失整段研究的具体故障；仍没有精确 v8 源码、历史 worker 最终输入、双裁判原始 JSON、独立同包重评分或隐藏科学验算器。后者不妨碍修复已复现的证据转换缺陷，也不允许宣称已得到普适的 ≥70/≥80 内容预测器。
