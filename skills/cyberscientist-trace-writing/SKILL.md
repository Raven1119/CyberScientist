# 轨迹：先过门，再谈分数

**为什么重要**：展示分 = 科学分 × 轨迹因子。轨迹分 ≥70 为 accept，展示分等于科学分；低于 70 为 review，按比例打折；block 为 0。S4 科学分 ≥90 的提交中，只有 46% 过了门，29% 直接归零。轨迹分 = min(0.55×检查表 + 0.25×来源证据 + 0.20×(100−作弊风险), 各封顶值)。常见封顶：29（block）、69（review）、49/39/59（review）、20（block）。

## 一、求解过程中就要留下证据（叙述补不出没做过的事）

1. **可见地创建代码**：题目特定的脚本和推导，用写文件命令或编辑工具在轨迹中写出（代码内容出现在轨迹里），然后运行。不要运行轨迹之外已经存在的完整脚本。
   - 否则触发 N17：产物先于轨迹存在，accept 率 0；
   - 或触发 N18：过程证据不足，挡住满分；
   - 或触发 N16 蒸馏：重放他人或其他 Run 已解出的题目特定工作，−100，block。
2. **产物有因果链**：每个提交文件都由轨迹中一条可见命令生成，路径与包内一致，写完立刻回显关键内容。否则触发 N11，它出现在 71% 的提交中。
3. **用题目要求的方法**：最终数值必须来自题目要求的方法，替代方法只用于探索、对照或保底。否则触发 N14，出现在 32% 的提交中。
4. **调用都有结果**：失败或中断也要留下输出（N08）；没有执行结果支撑的计算不能写（N09/N06，accept 率 0）。
5. **打印关键数字**：中间值、收敛过程、误差、最终值都打印出来。科学分 ≥90 却没过门的提交，最常缺的是：方法实现细节、代码与数据来源、原始工具输出、中间推导、独立验证、优化日志。
6. **独立验证**：至少一次单独运行的交叉检查，打印"一致/不一致"和差值。

## 二、写给裁判看

- 裁判对每个事件只看前 900 字符，题面只看前 5,000 字符，文件只看前 40 个，看不到图片内容；约 17% 的"缺证据"是写在了看不到的位置。
- 每段输出先打印结论和关键数字（例如 `RESULT x=… err=… PASS`），细节放在后面或写进文件，只打印摘要。
- 一个事件只做一件事；不要重复粘贴相同内容（N12，accept 率 0）。
- 时间戳、耗时、token 数必须真实，不要改写（N15，accept 率 0）。

## 三、叙述文件（trace_narrative.jsonl）

在当前 Trial 的 `trace_narrative.jsonl` 写一行一个步骤，用 `cs_refs` 指向本 Run 的真实 `run_id#seq` 事件，解释意图、动作、观察、失败修复和产物。工具 ID、输出原文、退出码、时间、费用、artifact 哈希必须与引用记录一致；事后写的解释用 `annotation: true` 加写作时间，不充当工具步骤。

叙述只能组织已有的证据，补不出缺失的证据：缺证据时，回到求解环节实际去做。写完用 `research_trace_narrative_check` 检查；未被叙述覆盖的事件投影仍会进入封存轨迹。

## 四、提交前自查

逐条对照 `cyberscientist-submission-gate` 的检查清单，并查看本地 v8 确定性检查的结果。本地复刻裁判在 S4 留出集上没有达到可用精度（判定准确率 54–62%），**只能作提示，不能作依据**。
