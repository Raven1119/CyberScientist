# 提交前检查（PI 用）

提交由你用 kind=submit 的指导发起。系统负责打包（官方 CLI，加上执行者的原生会话）、账号轮换、上传和取回回执。

**先交一版**：有了第一个完整结果就提交。回执是最有价值的信号；更细的收敛和敏感性分析放在提交之后。下面几点是交之前要过一遍的，不是让你追求完美。

## 科学
1. 结果在科学上站得住：输出完整、基本物理或逻辑检查通过、在所用设置下收敛。题目要求时才需要第二种方法交叉验证。并逐条对照研究简报里的“评分在查什么”。
2. 最终结果来自题目要求的方法；替代方法只用于探索或对照。
3. 这是手上现在最好的版本；不是第一次提交的话，相对上一次要有实质变化。

## 交付
4. 题面输出契约中的每个文件都在结果包里，文件名、路径、格式、字段与契约一致。
5. 交付文件中的数值与执行者会话里最后一次生成时打印的一致。

## 证据（执行者会话就是提交轨迹）
6. 题目特定代码在会话中可见地写出再运行；每个交付文件都有生成它的可见命令；关键数字已打印。
7. 会话中没有凭据，没有编造的工具结果或时间。

缺了哪一项，让执行者补上再交。轨迹不必追求完美，稳过 accept（轨迹分 ≥70）即可，写法见 cyberscientist-trace-writing。第一次提交不需要只读审查者。

## 系统会处理的
- 提交前的结构预检、凭据检查、官方 CLI 试构建；
- 同题连续提交自动换账号；提交不限次数；
- 平台明确拒收（达到上限、包未通过校验）时换账号或报错；状态未知时先对账，不盲目重发；
- 关卡拦截（例如凭据检查形状命中）由监控复核，结论会送到你这里；先等，不要马上改走干净复跑；
- 科学分先到，轨迹分和判定稍后；“人工复核中”的提交不影响继续迭代。

## 回执之后
- 科学分高且 accept：继续改进科学，或结束本题。
- 科学分高但没有 accept：按干净复跑策略发起，交接写法见角色说明。
- 科学分不理想：对照回执判断是方法、口径还是交付格式的问题，改进后再交。
- 回执出现 missing_worker_submission 或 nonstandard-submission-guard：这是提交链路问题，由系统和监控处理，不要改科学内容。
